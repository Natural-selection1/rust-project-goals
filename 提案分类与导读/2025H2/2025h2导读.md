# Rust 2025 H2 提案导读

大家好, 我是自然选择

美国时间 2025 年 10 月 28 日,
Rust 发布了 2025h2 共 42 个规划提案.

其中 18 个是之前就在推进的老项目,
也有 24 个全新提案!

我把这 42 个提案分成了 5 大类:

1. Cargo 与构建系统
2. 语言特性与人体工程学
3. 编译器内部与性能
4. 互操作性与平台生态
5. 规范、文档与测试

在这些新提案中,有不少重磅内容:
比如能大幅改善 rust 应用迭代开发体验的 `relink-dont-rebuild`、
万众期待的静态反射、
还有 Pin 人体工学的改进等等.

## Cargo 与构建系统

首先来看 `Cargo与构建系统` 的 3 个新提案, 可以说是精准打击痛点.

### `cargo-build-analysis` (Cargo 构建分析)

你有没有遇到过, 编译就是莫名其妙地慢,但你完全不知道是哪个环节出了问题？

// 展示 `./static/cargo build --timings` 相关文件

目前 Cargo 只有一个临时的 `--timings` 报告.
这就导致我们很难回溯和诊断构建问题.

这个提案要做的, 就是让 Cargo 把每次构建的详细元数据都记录、存储起来.
未来你就可以用一个新的 `cargo report` 去查询历史记录,
问问它:"上次为什么这么慢？" 或者 "哪个 crate 触发的重编译最多？"

这样一来,编译过程就不再是个黑盒了,问题能被看见,才能针对性解决.

### `cargo-build-dir-layout` (Cargo 构建目录布局)

再说第二个, 这个问题我相信很多人也都遇到过:

rust-analyzer 正在后台检查代码,
这时候你想在终端手动跑个 `cargo build`,
结果提示你 `target` 目录被锁定, 只能等待.

在大型项目中,这个问题尤其明显.
我之前给 rustc 提交代码的时候,就经常遇到这种情况,
有时候懒得等, 就直接重启电脑, 非常影响开发体验.

为什么会这样？

这是因为目前 Cargo 会锁定整个 `target` 目录,
一个进程在用, 其他进程就只能干瞪眼.

这个提案要做的, 就是彻底重构 `target` 目录的内部结构,
把每个编译单元的产物打包成更小的、独立的"单元".

这样一来, rust-analyzer 检查它的, 你编译你的,
大家可以更好地并行工作, 互相阻塞的情况会大大减少.

而且长远来看,这还能为未来的一些高级功能打基础,
比如用户级的共享缓存, 或者自动清理旧的编译产物等等.

### `relink-dont-rebuild` (重新链接而非重建)

第三个,也是我认为 这次 Cargo 相关提案里影响最大的一个.

现在哪怕只改了一个注释, 或者一个完全私有的、没有对外暴露的函数实现,
这个 crate 以及所有依赖它的下游 crate, 全部都要重新编译一遍.

// 展示 `./static/2024调查中的抱怨`

这绝对是现在 rust 应用迭代体验差的一个重要原因.
而且根据 Rust 基金会 2024 年度调查,
"编译太慢"就是开发者抱怨最多的问题.

这个提案要做的是让 `rustc` 和 Cargo 变聪明.
如果编译器判断你的修改没有动到这个 crate 的公共 API,
也就是说对外部没有任何影响,
那下游的 crate 就不需要 rebuild,
只执行成本低很多的 relink .

这个提案这要是能落地,
那日常开发中, 改点小东西就要等半天的痛苦就能大大缓解了.

我个人认为,这是 2025h2 所有新提案中, 最有影响力的一个

### 延续提案

当然,Cargo 这边还有一些之前就在推进的工作,也都在继续往前走:

- `build-std`:
  提供一个稳定的官方方式,让你可以按需自定义编译标准库.
  这对于一些没有预编译库的目标平台,或者需要特定编译优化的场景非常有用.

- `cargo-plumbing`:
  把 Cargo 从黑盒, 拆分成一系列模块化的底层命令,
  让其他工具能更灵活地与 Cargo 集成,不用再绕路.

- `cargo-script`:
  现在写个最简单的 Rust 程序, 最少也得创建 `Cargo.toml` 和 `main.rs` 两个文件.
  这个提案就是要让 Rust 支持 "单文件脚本",
  像 Python 那样, 一个文件就能跑起来,写点自动化小脚本会方便很多.

- `cargo-semver-checks`:
  在 `cargo publish` 的时候自动检查语义化版本,
  防止你不小心在小版本更新里引入了破坏性的 API 变更.

## 语言特性与人体工学

接下来看`语言特性和人体工学`, 这部分有 8 个新提案,
都是要啃一些 Rust 里长期存在的硬骨头.

### `reflection-and-comptime` (反射与编译期)

首先是静态反射.

像 Serde 这种序列化库,或者 Bevy 这样的游戏引擎,
它们需要能处理用户自己定义的五花八门的类型.
现在主要靠 `#[derive]` 宏展开,或者开发者手动实现一堆 trait.

// 展示 `./static/序列化宏示例`

提案旨在提供一个只能在编译期运行的、基于 `const fn` 的静态反射系统.
你可以写一种特殊的 `const fn`,
然后在编译的时候, 就能用代码去检查一个类型的内部结构了,
比如它有哪些字段、枚举有哪些变体等等.

这可能会彻底改变像 Serde、Bevy 这类库的编写范式.
它们可以变得更通用、更简洁,也许不用依赖那么多宏技巧了.

### `pin-ergonomics` (Pin 人体工学)

接下来是 `Pin 人体工学`,这个也很重要.

async Rust 性能很强, 但理解它、用对它的心智负担太重,
尤其是 `Pin` 相关的事情.

这个提案要做的是彻底改善 Pin 的使用体验,让它不再那么反人类.

核心想法是, 把 `Pin` 从一个库类型升级成语言的关键字, 就叫 `pin`,
然后为它设计原生、自然的语法.

具体来说有这么几点:

1. 引入新的借用语法 `&pin mut T`:
   设想一种新的引用类型,写作 `&pin mut T` 和 `&pin const T`.
   这种引用不仅像 `&mut T` 一样提供了独占访问权,
   还在类型系统层面就保证了它指向的数据是被 `pin` 住的.
   这使得 `pin` 这个概念, 从一个包装类型变成了一种原生的借用模式,
   更加清晰和直观.

2. 支持模式匹配 `&pin pat`:
   你可以直接对 `&pin` 进行模式匹配,
   就像处理普通引用一样,代码逻辑会更自然.

3. 支持自动解引用和方法调用:
   目标是让你能够像图示这样,
   直接在 `&pin` 上调用方法, 编译器会自动处理借用, 无需手动转换.

4. 与现有代码无缝衔接:
   如果一个类型是 `Unpin` 的,那么 `&pin mut T` 可以被自动"降级"为一个普通的 `&mut T`.
   这意味着你可以将一个 `&pin mut i32` 直接传递给一个期望 `&mut i32` 的函数,
   无需任何像 `Pin::get_mut()` 这样的显式转换.

如果这个提案能做落地,
那写异步代码的门槛和痛苦程度就能大大降低了.

### `in-place-initialization` (原地初始化)

第三个重磅提案是原地初始化.

你写过这样的代码吗:`Box::new([0; 1_000_000])`.

目前 Rust 并不原生支持原地初始化,
它会先尝试在栈上创建那个 1MB 的大数组, 然后再把它移动到堆上.
如果栈不够大, 程序就直接栈溢出了.

`原地初始化`就是为了解决这个问题,
允许值直接在它最终要待的内存位置被构造出来,
跳过那个中间的栈拷贝步骤.

但这只是 rust 没有原生原地初始化这个问题的冰山一角.
原生的原地初始化将解锁 Rust 在多个领域的关键能力:

1. 避免栈溢出:安全地构造超大对象.

2. C++ 互操作:
   C++ 的对象通常不是"可随意移动的",它们有复杂的构造函数和析构函数,
   必须在特定的内存地址上被创建.
   要在 Rust 中安全地创建一个 C++ 对象,你必须先分配好内存,
   然后调用 C++ 的构造函数在那块内存上完成初始化.这正是"原地初始化"的核心.

3. 与 C 语言 API（尤其是驱动和内核）高效交互:
   很多 C API 使用"出参指针"（out-pointer）的方式来返回值,
   例如 `create_foo(foo_t* out_ptr)`.
   调用者提供一个指针,函数在指针指向的内存里填充好一个结构体.
   "原地初始化"允许 Rust 代码安全、自然地与这类 API 交互,
   直接在 Pin 住的内存上完成初始化.这对于 Rust for Linux 项目至关重要.

4. 解锁 `async fn in dyn Trait`:
   这是目前语言的一大缺失.原地初始化是让动态分发的 async 函数成为可能的核心前提.
   因为 `async fn` 返回一个匿名的 Future 类型,其大小在编译时对 `dyn Trait` 的使用者是未知的.
   唯一的解决方案是:调用者提供一块内存,
   然后让 dyn Trait 的具体实现在调用者提供的内存上"原地"构造它的 Future.

5. 安全的自引用类型:
   允许在构造函数中安全地创建指向自身字段的引用,
   为实现侵入式数据结构（如侵入式链表）等高级模式铺平道路.

社区里其实已经有好几个库在尝试做类似的事情了,
比如 `pin-init`、`moveit`, 说明这个需求在社区里很强烈.

25H2 的目标主要是:先充分评估这些现有的探索方案,
然后确定下来官方打算走哪条路, 为后面的正式实现定个方向.
可以说, 原地初始化是 Rust 解决一系列底层问题、打通能力瓶颈的一个基础性工作.

### `autoreborrow-traits` (自动重借 Trait)

现在只有 `&mut T` 能自动重借, 就是你把它当参数传递的时候,
它不会被移动掉,而是自动为你重借用:

```rust
let mut data = vec![1, 2, 3];
let mut_ref = &mut data;

// 第一次调用,mut_ref 被"重借",而非"移动"
do_something(mut_ref);
// 第二次调用,mut_ref 仍然可用!
do_something_else(mut_ref);
```

但是,像 `Option<&mut T>` 这种包装层类型就不行了.
你传递的时候,它整个就被 move 走了.

但从语义上说,`Option<&mut T>` 只是一个可能为空的 `&mut T`,
它应该跟 `&mut T` 有相似的语义才对.

为了绕过这个问题,开发者不得不手动调用 `.as_mut()` 或 `.as_deref_mut()`.
这不仅代码冗长, 更严重的是, 它会引入更严格的生命周期限制,
使得某些复杂的 API 模式无法实现.

这个提案要把 "自动重借" 这个行为,
从编译器内置的魔法, 变成一个公开的 Trait.
以后, 只要类型实现了这个 Trait,
它也能像原生的 `&mut T` 一样,自动重借了.

这意味着什么？

能简化代码,少写点 `.as_mut()`,而且对 `pin-ergonomics` 提案
和 Rust for Linux 里那些自定义的指针类型也很重要.

它能让编译器中的重借特例, 被优雅的通用机制所取代,
也能解锁更强大的 API 设计.

### 其他新提案

语言特性这块还有几个新提案,简单说一下:

- `delegation`（委托）:
  顺带一提,在我写稿的时候,这个提案已经被拒绝了.
  它本来是想通过简单的语法糖,将一个类型的 trait 实现自动"委托"给它的某个字段,
  从而减少 newtype 模式中的模板代码.

- `evolving-traits`（进化 Trait）:
  允许在不破坏向后兼容性的前提下,为一个已有的 trait 添加新的 supertrait.
  这将解锁如 "为`Deref`添加 supertrait `Receiver`" 等重要的标准库演进的能力.

- `comprehensive-niche-checks`（全面 Niche 检查）:
  在调试模式下,为 `NonNull`、`NonZeroUsize` 等带有"无效值"（Niche）的类型添加运行时检查.
  这对于提升 FFI 和 `unsafe` 代码的健壮性很重要.

### 延续提案

语言特性这边还有一些之前就在推进的工作.
对普通开发者来说也挺实用的.

#### `field-projections`（字段投影）

`以下U均为T的一个字段的类型`
允许你直接通过 `Pin<&mut T>` 获得 `Pin<&mut U>`
或 通过 `MaybeUninit<T>` 获得 `MaybeUninit<U>` 这类智能指针访问其内部字段,
让智能指针在访问内部字段时, 像 `Box` 一样无感.

#### `ergonomic-rc`（人体工程的引用计数）

在 2025H1 中,已经实现了一个 nightly 可用的方案,
解决大量 `Arc<T>.clone()` 的问题:

```rust
let config = Arc::new(load_config());
let database = Arc::new(connect_db());
let metrics = Arc::new(MetricsCollector::new());
spawn(use async {
      ^^^ 注意这个 `use` 关键字
    // config, database, metrics 将自动克隆
    process_request(config, database, metrics).await;
});
```

社区反馈比较复杂, 大家都觉得很好, 但对易用性提出了质疑
所以 H2 的计划是继续探索其他的、更自动化的方案,
最好能不引入/复用关键字, 就把事儿解决了, 真正提高异步 Rust 的人体工学.

#### `unsafe-fields`（不安全字段）

目前,Rust 缺乏表示 "字段携带不变式" 的机制,
也没法强制说,修改某个字段的时候必须小心.

比如 `Vec` 的 `len` 字段的值永远不能超过 `cap`, 这是一种不变式.
但在当前的 Rust 中,这些规则只存在于注释和程序员的脑中,编译器对此一无所知.
这意味着, 任何 `safe` 代码都可以修改这些字段, 埋下导致未定义行为的 "定时炸弹".

这使得审查代码的安全性变得困难,
因为风险点散布在所有可能接触到这些字段的 `safe` 代码中.

提案允许你把某些字段标记为 `unsafe`.
这样编译器就知道, 要修改这个字段, 必须在 `unsafe` 代码块里进行.
这样就能把真正危险的操作隔离起来, 也更容易审计代码的安全性.

```rust
struct Vec<T> {
    // SAFETY: len 必须小于等于 cap
    unsafe len: usize,
    unsafe cap: usize,
    ...
}
```

### 其他延续提案

- `const-generics`:继续稳定化 const 泛型中剩余的功能.
- `open-namespaces`:允许通过包名扩展 API 命名空间.
- `pub-priv`:稳定化公共/私有依赖项,帮助开发者更好地控制 API 边界.

## 编译器内部与性能

编译器内部和性能优化, 这块最引人注目的新提案就是

### `production-ready-cranelift`（生产就绪的 Cranelift 后端）

我们都知道, Rust 默认用 LLVM 作为后端.
LLVM 优化代码质量很高, 但编译起来挺慢的, 尤其是开发阶段的 debug build.
Cranelift 是另一个编译器后端, 它的设计目标就是快——编译速度快.

这个提案要把 Cranelift 打磨到"生产就绪"的状态,
让它足够稳定、功能足够完善, 可以成为开发者在本地开发调试
比如跑 `cargo build/run/test` 以及成为 CI 环境里的一个可靠选择.

这意味着以后你可以在 `Cargo.toml` 里改个配置,
让你的 debug 构建用 Cranelift 来跑, 从而大大缩短编译等待时间.
这可以说是直接回应了 "编译太慢" 这个最大的抱怨点.

开发用快的 Cranelift, 发布时再切回优化更好的 LLVM,
这是一种非常可能的用法.

当然, Cranelift 目前还有一些功能需要追赶 LLVM,
比如像栈展开（unwinding）的支持、某些复杂 ABI 的兼容性、
还有一些 SIMD 指令集的支持, 这个提案就是要集中力量去解决这些遗留问题.

### 其他新提案

剩下的两个新提案都是编译器内部的优化工作, 简单提一下:

- `mir-move-elimination`（MIR 移动消除）
- `codegen_retags`（在代码生成中发出 Retag）

### 延续提案

在延续提案中, 最引人注目的就是

#### `polonius`:下一代借用检查器

Polonius 确实是大家持续期待的一个项目, 它也还在继续开发中.
25H2 的目标是希望能拿出一个相对成熟的版本, 可以开始进行稳定化的评估工作了.

Polonius 主要是想解决什么问题？

主要是想解决当前借用检查器 NLL（非词法作用域生命周期）有时候过于保守的问题.
就是说, 有些代码我们人眼看是逻辑安全的, 但 NLL 会拒绝编译.

最典型的例子就是那个对 `HashMap` 先调用 `get_mut` 获取一个可变引用,
然后再调用 `insert` 插入新元素的模式:

```rust
// 这段代码在当前的 Rust 下无法通过编译
fn get_or_insert(map: &mut HashMap<u32, String>) -> &mut String {
    match map.get_mut(&1) { // 第一次可变借用
        Some(v) => v,
        None => { // 理论上,到这里时 `get_mut` 的借用已经结束
            // 第二次可变借用,安全,但 NLL 认为与第一次冲突
            map.insert(1, "default".into());
            map.get_mut(&1).unwrap()
        }
    }
}
```

明明我知道这两个操作不会冲突,但编译器就是不让过.

NLL 无法分析出 `None` 分支中第一个借用已经结束,
因此错误地报告了借用冲突,迫使开发者使用 `entry` API 等更迂回的方式来编写代码.

Polonius 基于更精确的程序流分析算法,
它能更好地理解代码中借用的生命周期和作用范围,
从而能够接受更多像这样 NLL 会拒绝、但实际上是安全的代码模式.

最终目标是提升 Rust 的人体工程学,
减少开发者（尤其是新手）跟借用检查器"搏斗"的时间和挫败感,
让 Rust 代码写起来更顺畅、自然, 同时也能降低学习曲线.

#### 其他延续提案

- `parallel-front-end`（并行编译器前端）:
  让编译器前端能并行处理.
  这个工作已经取得了不错的进展, 现在已经能带来 20%-30% 的编译速度提升.
  目标是稳定化这个成果.

- `next-solver`（下一代 trait 求解器）:
  主要是为了修复当前求解器的一些健全性问题,并且提升性能.

- `a-mir-formality`:
  这个更理论层面的工作,用形式化方法来验证 Rust 的类型系统的安全性.

## 互操作性与平台生态

互操作性和平台生态主题有 6 个新提案,
旨在打通 rust 与其他技术生态的连接.

### `finishing-gpu-offload`（完成 GPU 卸载）

GPU 卸载 是一种计算技术，
将原本由 CPU 处理的、计算密集型任务转移到 GPU 上执行.

Rust 强大的别名信息为这些领域带来了显著的性能优化空间，
其性能提升远超 C++ 与 Rust 的常规对比表现。
这主要得益于 自动微分和 GPU 卸载技术能够充分运用别名信息实现性能提升.

但现在你要用 Rust 在 GPU 上跑计算,
基本上得依赖 `rust-gpu`、`wgpu` 这样的第三方库.

这个提案要完成 `std::offload` 模块的开发.
这意味着 Rust 将拥有内置的、一等的 GPU 编程能力.
未来，开发者将能够编写单个 Rust 函数，
使用 `std::batching` 获取其 SIMD 或 算子融合 版本，
使用 `std::autodiff` 对其进行微分，
并使用 `std::offload` 在 GPU 上运行生成的代码。
机器学习或线性代数库将能够通过选择基于 MLIR 的新编译器后端来进一步优化性能,
该后端会自动重写计算密集型操作以获得更好的性能.

### `stabilization-of-sanitizer-support`（稳定化 Sanitizer 支持）

尽管 Rust 本身提供 内存访问安全 和 线程访问安全 的保证，
但在混合语言二进制文件中使用 Unsafe Rust 及外部代码时，
这些保证将不再适用。

因此，必须在 Rust 编译器中加入 sanitizer 支持，以保障 Rust 的安全采用.
像 MemorySanitizer、ThreadSanitizer 这些工具,
对发现 `unsafe` 代码、FFI 接口里的内存错误、数据竞争这些问题非常有用.
并且这些工具在 C++ 里用的很多.

但目前在 Rust 中使用它们比较麻烦,
不仅需要用 Nightly 版本的工具链,
而且通常还得自己手动去编译一个打了桩的标准库.

这个提案要做正式稳定化对这类 Sanitizer 的支持,
并且更关键的是, 通过 `rustup` 直接提供预编译好的、已经插桩的标准库.

这意味着以后在 stable Rust 上也能开箱即用地跑这些 Sanitizer.
拓展 rust 的安全边界.

### `interop-problem-map`（C++/Rust 互操作性问题图谱）

C++ 在其 40 年发展历程的大部分时间里始终是领先的系统编程语言。
现有数十亿行 C++ 代码库承载着数万亿美元的价值。
短期内大规模重写当前活跃使用的 C++ 代码既不可行也不明智。
从谷歌, 微软等公司的实证表明，使用内存安全语言编写新代码能带来显著更大收益。
这使得在 C++ 代码库中开展 Rust 开发变得至关重要.

这个提案是一个基础性的组织和调研工作.
目标是创建一个权威的 "问题图谱" 或者说路线图,
系统性地梳理清楚 rust 与 C++ 之间进行互操作时会遇到的技术挑战,
比如说 ABI 兼容性、头文件的处理、错误处理机制的对接、
生命周期和所有权怎么映射, 等等.

这份问题图谱, 就是要凝聚社区的共识, 明确挑战所在,
为未来设计更好的互操作工具和方案,
无论是在 Rust 层面、C++ 层面, 还是在底层的 LLVM 层面打造一个坚实的基础.

### 其他重要提案

- `Rust-for-Linux-compiler`、`Rust-for-Linux-language`:
  继续推进让 Rust for Linux 内核开发工作能在稳定版 Rust 上进行的旗舰提案.
  需要把很多内核依赖的编译器特性（比如各种 `-Z` 标志）
  和语言特性（比如 `arbitrary_self_types`）给稳定下来.

- `gcc-backend-tests`:
  为 `rustc_codegen_gcc`（GCC 后端）在 Rust 的 CI 中运行更多测试,
  以更快地发现回归并加速其开发进程.

- `scalable-vectors`（延续提案）:
  继续为 ARM SVE/SME 等可伸缩向量指令集提供支持,
  这对于现代硬件上的高性能计算至关重要.

## 规范、文档与测试

规范、文档和测试主题有 5 个新提案,
旨在让 Rust 的知识体系更完善、更易于访问, 并提升社区的贡献体验.

### `reference-expansion`（扩展 Rust 参考）

Rust Reference 是官方的核心语言文档, 但它其实还不够完善.

比如像类型推导的具体规则、trait 求解的详细过程、
名称解析的优先顺序、宏扩展的具体机制等等,
这些核心的语言机制在 Reference 里的描述还不够深入和精确,
有些地方甚至还是空白.

这个提案要做的是组织一个由多位专家组成的团队,
为 Reference 撰写新的章节, 系统性地填补这些空白.

一个更全面、更精确的语言参考, 将使 Rust 的行为不再模糊不清,
为所有用户和实现者提供一个可靠的真理来源.

### `rustdoc-doc-cfg`（稳定化 rustdoc 的 `doc_cfg` 特性）

大家平时查标准库或者其他库的文档时,
会不会经常遇到看到一个函数或者类型, 但不确定它是否在所有平台上都可用？
或者它是不是需要开启某个特定的 feature flag 才能用？

现在只能靠文档作者在说明里手动写, 否则只能自己看源码

这个提案要稳定化 `doc_cfg` 功能.
启用后, `rustdoc` 在生成文档的时候,
就能自动识别出那些受条件编译 `cfg` 影响的 API 项,
然后自动给这些 API 项加上一个非常醒目的标记,
比如说 "仅在 Windows 平台可用" 或者 "需要启用 `serde` 特性".

### `typesystem-docs`（类型系统文档）

这个提案是专门针对 Rust 复杂但又核心的类型系统,
比如常量泛型、新的 trait 求解器等来编写文档.

它现在有点像个黑盒子, 尤其是对想参与编译器开发的新人来说门槛很高.

这个提案希望能系统性地把类型系统的关键组件讲清楚,
降低理解和贡献的难度, 也让审查那些复杂的类型系统相关的改动能更容易、更可靠.

### 其他重要提案

- `FLS-up-to-date-capabilities`:
  为形式化语言规范（FLS, 主要用于安全关键领域）建立一套流程,
  使其能与 Rust 语言的发展保持同步.

- `rustdoc-team-charter`:
  为 rustdoc 团队制定一份正式的团队章程, 明确其流程和成员职责.

- `libtest-json`（延续提案）:
  完成 libtest 的 JSON 输出实验,
  为 `cargo-nextest` 等高级测试工具和 Cargo 内置的测试报告提供支持.

- `rustc-perf-improvements`（延续提案）:
  继续改进 rustc-perf 性能追踪基础设施,
  以支持在多平台、多配置下进行分布式基准测试.

- `rust-vision-doc`（延续提案）:
  继续为 Rust 愿景文档进行数据收集（访谈）,
  以确保其结论建立在对各类用户需求的充分理解之上.

## 总结

看完这 42 个提案, 总的来说, 可以梳理出几条比较清晰的主线:

感受最明显的就是 rust 正在努力提升开发者的开发体验.
rust-analyzer 和 cargo build 不再相互锁定.
迭代应用中重编译次数大幅减少,
更强大的 cargo 插件, pin 可用性大幅提升,
包装可变引用的自动重借, Arc 的闭包中的自动克隆,
更聪明的借用检查器, 并行的前端编译, 更快的后端编译

第二就是增强语言本身的表达力,
比如反射、原地初始化、字段投影、不安全字段和 evolving-traits.

第三是拓展 Rust 的应用边界.
更好地融入现有生态, 比如 GPU 支持、Sanitizer 工具、C++ 互操作.
`Rust-for-Linux-compiler` 和 `Rust-for-Linux-language`

最后就是规范化, 完善缺失的 rust 内部复杂问题的文档.

你会发现很多提案都在简化 Rust 中那些经常被认为复杂、学习曲线比较陡的部分.
所以我觉得完全不需要担心 rust 未来会变成下一个 cpp,
更何况有 Edition 机制在, 失误设计都可以通过 Edition 进行隔离.

最后我想特地提一下 `rust for linux project` 对 rust 语言演进的巨大推动作用,
在 2025h2 19 个非文档新提案中, 有 5 个与其直接相关.
在 `rust-for-linux-language` 中, 更是有这样的描述.

如果说 python 在经历 `2升3` 的动荡后被 AI 需求复活,
那么 rust 的生命力则可以说是被 `rust for linux` 点燃.
