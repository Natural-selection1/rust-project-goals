# 编译与构建

## cargo-cross-workspace-cache

只要你写过多个 Rust 项目, 必然会意识到一件荒诞的事实:

一些通用的大库, 比如 `syn`, `tokio`
每个项目都要自己独立编译一遍.

明明这些依赖的版本、features、编译参数都可能完全一样,
但因为它们属于不同 workspace,
Cargo 默认还是会把构建产物放在各自的 `target` 目录里.

于是每个项目都有自己的一套缓存,
这不仅导致很多常用 crate 在不同项目里被反复编译,
也导致了磁盘空间的极度浪费.

目前, 你可以通过环境变量 `CARGO_TARGET_DIR`,
设置全局编译产物的目录来缓解这个问题.

但这并不是 Cargo 原生语义的一部分, 副作用包括:
`cargo clean` 会清除所有项目编译产物,
以及输出二进制不再落在当前项目里

这个提案要做的, 是让 Cargo 自己理解"跨 workspace 共享缓存"这件事.

在 2025 年, 已经完成了一些铺垫工作.
它将原来的 `target-dir` 拆成了更清晰的 `artifact-dir` 和 `build-dir`,
并开始按照 构建单元 重新组织构建产物布局.

只有当 Cargo 能清楚地知道
"这个产物到底对应哪个 crate、哪个 feature 集、哪些编译参数",
它才有可能安全地复用这个产物.

2026 年的目标, 是在这个基础上设计并实现一个跨 workspace 的共享缓存.

理想情况下, 当你在一个项目里已经编译过某个依赖,
其他参数相同的项目就可以直接复用它, 而不是重新从头编译.
这也可能在未来扩展到 CI 场景, 比如预先从远程缓存填充常用构建产物.

- 2026 目标页: https://rust-lang.github.io/rust-project-goals/2026/cargo-cross-workspace-cache.html
- tracking issue: https://github.com/rust-lang/rust-project-goals/issues/626
- Cargo build-dir layout rework: https://github.com/rust-lang/cargo/issues/15010
- Cargo cross-workspace cache tracking: https://github.com/rust-lang/cargo/issues/5931

## parallel-front-end

说完了编译占用空间的事情, 那自然也是要说说编译时间.

了解rust编译的观众应该都知道,
rust的编译时间瓶颈是LLVM和链接, 对此我们无可奈何.

但rust前端仍有一个充足的优化空间, 那就是将其并行化.

在目前的stable rust中, 单个crate的前端工作仅使用单个线程.
因为crate是rust的编译单元, 这其实无可厚非.
但对于没有拆分crate习惯的人来说, 会有非常糟糕的编译体验

提案的目标, 就是让前端更多阶段能够并行执行.
经过 25h1 和 25h2 两个提案周期的打磨,
以单线程性能下降2%换取了30%的clean debug build编译时间.
并且其即将进入 CI 流程, 这几乎意味着其将于最近的一年内稳定化.

### incremental-system-rethought

`incremental-system-rethought`

拿到一个项目, 你可能会先跑 `cargo check`,
然后 `cargo build`, 最后 `cargo test`.

从人的角度看, 这三件事有大量重叠工作.
但从当前增量系统的角度看,
不同编译器调用之间并不能充分共享这些进度.
于是很多东西会被重复计算.

这个提案希望重新设计增量系统,
让 `cargo check`、`cargo build`、`cargo clippy` 等命令
在兼容的情况下共享更多共同基础.

比如先 `cargo check` 再 `cargo build`,
后者应该尽量复用前者已经完成的解析、类型信息或依赖图结果,
而不是像没见过一样重新来一遍.

### mirroring

`mirroring` 讲的是 Rust 官方镜像和可验证分发.

Rustup 下载 toolchain, Cargo 下载 crate,
都依赖 Rust 项目的基础设施和 HTTPS 端点.

在 GitHub Actions 这类高流量环境里,
这不仅会带来带宽和日志成本, 也会带来供应链安全问题.
用户到底如何确认自己拿到的东西就是 Rust 项目发布的?

这个提案希望实现一个可验证镜像原型,
来验证镜像同步和分发内容.

# 工具链

### libtest-json

`libtest-json`

Rust 默认测试框架是 `libtest`.
你运行 `cargo test`, 它会发现测试、运行测试、输出结果.

但它的输出主要是给人看的文本.
想让工具稳定解析测试结果会比较麻烦.

这个提案的目标, 就是完成 libtest JSON 输出实验,
并重新划分测试 harness 和 test runner 的职责.

更理想的模型是:
测试二进制负责告诉 runner 有哪些测试、结果是什么;
Cargo 这样的 test runner 负责汇总、展示、并行调度和更复杂的 UI.

这样 `cargo nextest` 这类工具可以拿到更多结构化信息,
自定义测试 harness 的门槛也会降低.

目前 `libtest2` 已经基本成型, JSON schema 也在推进,
并且已经支持了 `#[test]` 宏、`should_panic`、`ignore`、
自定义错误类型等基础能力.

### mcdc-coverage-support

# 文档

Rust 的强大能力是构建在众多规则之上的, 但是很多规则的真正答案,
往往藏在 rustc 源码、Zulip 讨论或者专家脑子里, 而不是写在文档里.

在曾经rust只是路边小众语言时, 这不算是个问题.
但当 Rust 进入 Linux、汽车、航空这些领域时, 只靠"问懂的人"就不够了.

Rust 需要更明确的文档.

## a-mir-formality && experimental-language-specification && stabilize-fls-releases

很多时候, 我们知道 rustc 是怎么做的,
但很难用一个更高层、更适合推理的形式化模型来描述它.

`a-mir-formality` 就是为了做这件事.

它希望把 Rust 的类型系统、trait 系统、borrow checking 等核心规则,
用一种比 rustc 实现更抽象, 但又足够接近真实编译器的方式描述出来.

25h2 时, 这个目标主要集中在:
让 a-mir-formality 表示 MiniRust 程序,
实现 MIR type checker, 以及建模 Polonius Alpha 的关键部分.

现在它的方向又往前走了一步.
最新进展中提到, 已经有初步 codegen 模块,
可以把 a-mir-formality 表达式转换成 MiniRust 来执行.

也有人在做从 a-mir-formality 程序转换到真实 Rust 程序的工具.
这件事很重要, 因为它可以反过来比较:
形式化模型接受的程序, 真实 rustc 是否也接受.

如果两者不一致, 那就能发现模型太宽、模型太窄,
或者 rustc 行为本身需要解释的地方.

同时还有人在做正例和反例的 coverage report.
这说明它已经不只是"写一些规则",
而是在慢慢变成一个可以验证、可以对比、可以迭代的项目.

`experimental-language-specification`
是 25h2 `Reference expansion` 工作的延续.

25h2 的目标,
主要是补 Rust Reference 的缺口, 写新章节, 探索稳定性标记.

2026 年的重点不只是继续写 Reference.
它更想实验一种流程:
当 Rust 某个领域团队推进一个语言变化时,
对应的规范文本能不能更早、更系统地进入流程?

比如 const traits 这类变化,
不仅需要 lang team 决定语言长什么样,
也需要 types team 解释它的精确语义.

过去很多文档是在功能差不多完成后再补.
而这个提案希望让文档更早参与设计,
并通过 unstable markers 区分:
哪些是 unstable Rust feature,
哪些是 stable Rust 但文档文本本身还在实验中.

第三个是 `stabilize-fls-releases`.

FLS 是 Ferrocene Language Specification,
是 Ferrous Systems 公司为安全关键行业开发的 Rust 语言规范文档。
它详细描述了 Rust 的语法、语义和行为，
旨在满足高安全、高监管行业对编译器进行鉴定和标准化的要求.

因为做安全认证时, 你不能只说"rustc 大概就是这样".
你需要有对应版本的语言规格说明,
让审核、认证、工具链供应商都有依据.

2025年3月，Ferrous Systems 已将其捐赠给 Rust.

25h2 的重点是探索:
Rust 项目有没有能力持续维护 FLS?
需要什么团队、流程、工具?

这个目标已经完成, 并建立了 FLS team.
2026 年的 `stabilize-fls-releases`,
则把问题从"能不能维护"推进到"按什么节奏稳定发布".

它的目标很明确: FLS N 要在 Rust N stable 发布后的六周内发布.

也就是说, 在 Rust N+1 出来之前,
上一个稳定版本对应的 FLS 应该已经准备好.

这样规范发布有了可预期节奏,
相关组织才能围绕 Rust release train 安排认证和交付计划.

这三个提案其实是在回答同一个问题:
Rust 不能只靠编译器源码定义自己.

它需要 Reference, 需要 FLS, 需要形式化模型,
也需要把这些东西接入真实团队流程.

## improve-std-unsafe && safe-unsafe-for-safety-critical && typesystem-docs

第二组文档提案, 可以概括为:
把专家脑子里的安全和类型系统知识写出来.

Rust 标准库里有大量的 unsafe API.
这些 API 通常会有 `# Safety` 文档, 告诉调用者必须满足哪些条件.
但现实中, 这些 safety 文档并不总是一致、完整、系统.

有些 unsafe API 可能缺 safety section.
有些函数的安全前提隐藏在被调用函数里, 但没有被上层 API 明确写出来.
有些命名规则其实暗含了安全约束, 比如某些 `_in` 后缀意味着指针必须来自特定 allocator,
但文档不一定把这些约束讲清楚.

`improve-std-unsafe` 提案要做两件事.

第一,
系统审查标准库 unsafe code 文档,
找出缺失 safety section、缺失安全性质、命名和参数暗含约束不清楚等问题.

第二,
从标准库审查中总结一套实验性的 unsafe code 文档和安全推理标准.

提案里有一句话很关键: `safety invariants go before unsafe`.

也就是说, 我们不能先随手把某个函数标成 unsafe,
然后再想它为什么 unsafe.

应该先明确这个类型或 API 到底有哪些 safety invariants,
再判断哪些操作可能破坏这些 invariants, 因此必须放进 unsafe 边界里.

第二个是 `safe-unsafe-for-safety-critical`.

它和刚才的提案相关, 但角度更偏安全关键应用.

安全关键项目不能只说: "这个 unsafe block 我感觉是对的".

它需要能够引用权威文档,
证明某种 unsafe 模式在满足哪些条件时是 sound 的.

但今天 Rust 的 unsafe 文档仍然有缺口.
虽然死灵书有一些额外内容, 但不是完整规范,
Unsafe Code Guidelines Reference 也不是规范性文档.

这个提案打算从真实代码库出发, 工作流程大概是:
先把 unsafe 模式分类, 找出缺少规范性文档的部分,
然后和 opsem team 一起确定正确的 safety 契约,
最后把这些内容补进 Rust Reference 或标准库文档.

第三个是 `typesystem-docs`.

Rust 类型系统是编译器里最复杂的部分之一.
许多内容都不是新贡献者随便读读代码就能懂的.

过去一个常见问题是:
如果你想理解某个类型系统组件, 最可靠的方法可能不是看文档,
而是去问 types team 成员, 这种模式显然不可持续.

25h2 时, 这个目标已经完成了一些基础工作:
整理出一大串需要文档化的类型系统主题,
并建立了 rustc-dev-guide 的 tracking issue.

目前已经有一些具体成果, 2026 年的目标, 就是继续挑重点补齐.

这一组提案的共同点是:
Rust 不只是要正确, 还要能解释自己为什么正确.

标准库需要一致的 safety 文档.
unsafe 需要可引用的安全契约.
类型系统需要让新人能自学的工程文档.
