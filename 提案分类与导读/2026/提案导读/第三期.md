# 语言特性: 易用性

## ergonomic-rc

只要你写过 async rust, 大概率都见过这种代码:

先把一堆 `Arc` clone 一下,
再通过 move 闭包值捕获这些 clone 后的变量.
有些时候, 逻辑本身的行数可能都比不上这些的样板代码.

这个提案旨在改善这种模式.
之前 RFC 3680 提出了 `.use` 语法和 `use ||` 闭包.
但社区反馈里有一个很核心的问题:
如果目标是提高易用性,
那新增 `.use` 和 `use ||` 这种必须解释的新语法,
会不会反而让代码更难读?

经过半年的讨论, 现在提案提出两个更基础的能力:

第一个是 `Share` trait, 它用来表达一种语义:
这个类型 clone 之后, 得到的不是一份独立数据,
而是指向同一个对象的另一个别名.

比如 `Arc<T>`、`Rc<T>`、channel sender, 都可以实现 `Share`.

这样一来, 代码里写 `tx.share()` 时,
读者就知道这不是深拷贝, 而是在创建另一个共享句柄.

第二个是 `move()` 表达式.
它让你可以把捕获动作写在使用位置:

<!-- 这里需要更细致地解释一下 move() -->

这两个特性合起来, 让代表 资源handle的克隆 在闭包里的使用更紧凑

```rust
tokio::spawn(async {
    send_data(move(tx.share())).await;
});
```

## afidt-box

Rust 在 1.75 稳定了 async fn in trait.
你可以写:

```rust
trait HttpClient {
    async fn fetch(&self, url: &str) -> Response;
}
```

但问题是, 这样的 trait 并非动态兼容.
原因在于 async fn 返回的是一个隐藏的 future.
动态分发时, 调用方不知道被调用者会返回多大的 future.

所以今天常见的解决方案是使用 `async-trait`
但它的问题是会改变 trait 定义本身:
trait 的实现者也被迫每次都返回 boxed future.

这个提案通过引入 `.box` 后缀表达式,
让 trait 定义保持原生 async fn, 保持泛型调用的零分配,
只有在你真的通过 `dyn` 调用时, 由调用点显式 box.

```rust
client.fetch(url).box.await
```

`.box` 的意思是:
我知道这里需要一次堆分配, 我也接受这个成本.

这与 Rust 的理念一致:
堆分配应该可见, 但也不要让用户为了表达常见模式写一大坨类型.

这个提案还会推动一个更细的概念: method-scope dyn compatibility.
也就是说, 一个 trait 不再只是简单地分成"整个 trait 是否动态兼容".
某些方法也许只有在指定分配策略时才能通过 dyn 调用.
这对 async trait 很重要, 未来对 RPIT 这类返回不定大小值的方法也可能重要.

## field-projections (延续提案)

如果你有 `let foo_ref = &mut foo`,
那你可以自然地写 `let bar_ref: &mut Bar = &mut foo_ref.bar`,
得到某个字段的可变引用.

但如果你手里不是普通引用,
而是 `Pin<&mut T>`、`NonNull<T>`、`&mut MaybeUninit<T>`,
或者某个自定义智能指针, 事情就没这么简单了.

这些类型在语义上明明也能指向那个结构体的字段,
但 Rust 目前并没有一个通用机制来完成这样的事情,

所以生态里会出现很多专门的宏和 crate,
比如 pin projection 相关工具.

这个提案的目标, 就是把这种能力推广到自定义指针类型.
25H2 时, 这个提案的重点还是找设计方向, 2026 提案则更进一步.

上一阶段形成了一个新方向, 叫 `virtual places`.
它的想法是:
不要只把字段投影理解成"拿到某个真实内存地址",
而是把它抽象成对 place 的操作.

因为有些类型的字段, 可能并不对应一个简单的真实内存位置.

提案里提到的设计会引入类似
`PlaceRead`、`PlaceWrite`、`PlaceMove`、`PlaceBorrow` 的 trait,
允许类型定制该如何读取、写入、移动和借用一个虚拟位置.

这听起来很底层, 但它的最终目标其实很朴素:
让 `NonNull<T>`、`MaybeUninit<T>`、`Pin<&mut T>`、Rust for Linux 里的各种指针类型,
都能自然地访问它们的字段.

## pin-ergonomics (延续提案)

`Pin` 是需要 Rust 功能的重要基础, 但问题在于它写起来非常不舒服.
很多时候你只是想表达: 我现在要以 pinned 的方式借用这个位置.
但实际代码往往要绕过一堆 API、宏和 unsafe 边界.

25H2 时, 这个提案已经开始探索 `&pin mut place` 这样的语法,
还列出了 pattern matching、coercion、auto borrowing 等工作.
2026 年的版本仍然是继续实验, 但它把一个关键语义问题说得更清楚了.

普通 `&mut` 借用是临时的, 借用结束, 原来的 place 又恢复正常.
但 `&pin mut` 不一样, 一旦一个 place 被 pin 过,
这个 pinned 效果可能在借用生命周期结束后仍然存在.

也就是说, 你不是"临时借一下",
而是在程序语义里永久改变了这个位置的可移动别.

相较于 25H2, 它不是简单地"继续把语法写完",
而是把重心推进到了 borrow checker 支持、coercion、auto borrowing,
以及这种新借用行为是否可理解的问题上.

# 语言特性: 编译期能力

## const-generics (延续提案)

今天 Rust 已经稳定了 const generics 的 MVP,
你可以写类似 `[T; N]` 这种带常量参数的类型.

但它仍然有两个很明显的断崖:

第一, const generic 参数类型很有限.
主要是整数、`bool`、`char`.
目前不能把 ADT 当成 const 参数.

第二, const 参数位置能写的表达式也很有限.

比如你想写 `Foo<T::ASSOC_CONST>`,
使用某个关联常量作为 const 参数,
现在仍然会遇到限制.

25H2 时, 这个提案主要目标是:
为 `adt_const_params` 整理设计文档和 RFC,
并继续完成 `min_generic_const_args` 原型.

2026 年的目标更清楚:

一条线是 `ADT const params`.
也就是让 struct、enum、tuple、array 等 ADT 可以作为 const 参数.

另一条线是 `min_generic_const_args`.
也就是让关联常量和泛型参数能更自然地出现在 const 参数表达式里.

## const-traits

今天很多代码其实都适合放到编译期跑,
比如构造查表数据、校验常量、做一些可提前计算的泛型逻辑.

但只要逻辑里涉及 trait, 就很容易撞墙.

比如你想在 const fn 里使用 iterator,
或者用 `?` 处理 `Result`, 它们背后都依赖 trait.

如果 trait 方法不能在 const 上下文调用,
那 `const fn` 的泛型能力就会被大幅削弱.

这个提案的状态比较有意思:
编译器里已经有相对成熟的 const traits 实验实现,
标准库里也已经有部分代码开始使用.

但它还缺一个被正式接受的 RFC, 来确定语法和语义.

所以 2026 年的目标就是:
继续完善 const traits RFC,
处理现有反馈, 补齐必要的编译器工作,
发起测试, 然后推进稳定化.

如果 const traits 能稳定,
它会让 `const fn` 从"只能写比较直接的过程逻辑",
变成"可以写真正泛型化的编译期逻辑".

## reflection-and-comptime (延续提案)

今天 Rust 生态里, 如果你想让一个库处理任意用户类型,
最常见的方式是让用户 derive 某个 trait.

比如序列化需要 `#[derive(Serialize)]`,
游戏引擎可能需要 `#[derive(Component)]`,

这带来一个问题: 库之间互操作很难.

每个库都希望用户为自己的类型加 derive,
但类型作者不可能为所有潜在库都提前写好实现.

这个提案想探索另一条路:
在编译期通过 `const fn` 获取类型信息,
让库可以对任意类型做结构化处理,
而不一定要求用户提前 derive.

25H2 时,
这个提案的目标还是:
设计并实验性落地一个基于 `const fn` 的反射方案,
同时加一个只能编译期调用的 const fn 机制.

2026 年的文档里出现了一个很关键的进展:
MVP 已经落地.

它实现了 `TypeId::info`, 可以返回一个 `Type` 结构,
里面包含类型种类等信息.
现在还在逐步增加更多 `TypeKind`,
并且已经有基础的 comptime fn PR 在推进.

2026 年的目标, 是继续完善这个实验:
增加 `Type` 和 `TypeKind` 信息,
处理跨模块访问 private 字段时的隐私问题,
给 const fn 加只能编译期调用的属性,
并最终争取 lang 和 libs-api 的认可.

作为 MVP 的推进, 它明确把范围限制在:
产生 const eval 值, 让程序可以在编译期读取类型结构信息.
至于把类型信息重新塞回类型系统, 那是后续阶段的事情.

## macro-improvements

Rust 的宏系统有两大类: 声明式宏 和 过程宏.

声明式宏编译快、无依赖、能使用 `$crate` 等机制, 但能力有限.

过程宏能力强, 但缺点也明显:
必须单独建一个 crate,
引入 `syn`、`quote`、`proc-macro2` 等重依赖,
也会拖慢 `cargo check`.

这个提案的初始目标,
是稳定声明式 attribute macro 和 declarative derive macro.

也就是说, 让一部分今天必须用过程宏写的东西,
未来可以用更轻量的风格表达.

更长期看,
这个提案还会探索 macro fragment fields、metavariable expression,
以及和 reflection/comptime 配合的 `macro fn`.

# 基础设施: 平台与互操作

## interop-problem-map (延续提案)

现实世界里有大量 C++ 代码, 不可能短期全部重写成 Rust.

如果 Rust 想进入这些代码库,
就必须能和 C++ 高效、安全、可维护地互操作.

今天我们已经有 bindgen、cbindgen、cxx 等工具.
但这些工具各有假设, 并没有一个共同的语言级或标准库级基础.
这导致很多互操作问题被分散在各处.

提案的目标不是立刻设计一个统一方案, 而是先把问题空间整理清楚.

25H2 时, 这个提案已经提出要整理 C++/Rust 互操作问题空间.
现在则明确地把交付物定为 interop initiative repo 里的离散问题陈述.

## overloading-for-ffi

C++ 支持函数重载.
同一个函数名可以根据参数个数、参数类型、receiver 类型选择不同实现.
但 Rust 没有这种形式的函数重载.

如果用 Rust 调 C++, 现在的办法通常是:
给每个重载函数起不同名字, 或者用 trait 模拟,
或者由工具生成 `foo1`、`foo2` 这种编号函数.

尤其是对 C++ 库维护者来说, 如果只是新增一个重载,
C++ 调用者可能没什么影响,
但 Rust binding 可能要重新命名、重新生成、甚至破坏已有调用.

提案希望设计一种适合 FFI 的函数重载机制.
它不要求 Rust 完全复制 C++ 的重载解析规则,
比如不会去实现 C++ 那套 ADL.

但目标是:
每个 C++ 重载都应该能从 Rust 调用, 而且新增或删除重载时,
Rust 侧的维护成本不要明显高于 C++ 侧.

提案提到的方向, 是尽量复用 Rust 已有 trait 系统,
可能结合 `extern "rust-call"` 或参数 splatting,
做一个 nightly 语言实验.

## open-enums

Rust 里 `#[non_exhaustive]` 可以告诉用户:
这个 enum 未来可能加变体,
所以你 match 的时候不要假设它已经穷尽.

但这只解决源码一起编译时的模式匹配问题.

如果两个编译单元分别编译,
一个版本的 enum 后来新增了变体,
另一个旧版本代码并不知道这个变体,
那就可能出现 ABI 层面的未定义行为.

C enum 在这方面更像一个开放整数集合.
它可能有几个已命名值,
但外部代码也可能传入还没被当前头文件命名的值.

bindgen 今天为 C enum 提供多种表示方式:
整数常量、模块常量、newtype struct、Rust enum.
但每种都有明显缺点.

如果用 Rust enum, 遇到未知值可能 UB.

如果用 newtype struct,
又失去了 enum 的语义、工具支持和 derive 生态.

这个提案想合并并实现 unnamed enum variants RFC.

大致想法是:
允许在 `repr(C)` field-less enum 里声明一段未命名但有效的 discriminant,
比如用 `_ = ..` 表示未来或外部传入的值也是有效值.

这样它仍然是 Rust enum,
但又能表达开放枚举的 ABI 语义.

这对 bindgen、C 互操作、动态链接和未来可扩展 ABI 都很重要.

## libc-1.0

`libc` crate 是 Rust 调 C API 时最常依赖的底层包,
是 Rust FFI 生态的核心基础.

但它长期停在 0.2, 不是因为没人想发 1.0,
而是因为 1.0 意味着稳定承诺, 现在还有一些历史问题没解决:

例如 32 位平台上的 `time_t`、`off_t` 到底是 32 位还是 64 位,
会受到 C 头文件和宏配置影响.

但 Rust crate 不能像 C 头文件那样根据宏动态改变类型定义.

还有一些早期 API 或 ABI 错误,
比如错误类型定义、`iconv`、`vfork`、占位常量等等,
都可能需要 breaking change.

提案的目标是把 1.0 blocker 系统处理掉,
补完测试基础设施, 明确 MSRV 和平台支持政策,
最终为 libc 1.0 做发布准备.

## aarch64_pointer_authentication_pauthtest

Pointer Authentication, 简称 PAC,
是 ARMv8.3 引入的硬件安全机制.

它会给指针加一个加密签名, 在使用指针前验证签名,
从而防止攻击者篡改返回地址、函数指针等控制流相关指针.

LLVM 和 Clang 生态已经有相关支持,
AArch64 ELF 平台也有对应 ABI 扩展.
但 Rust 编译器今天还没有完整支持.

这会带来两个问题.

第一, Rust 不能正确和启用 PAC 的 C/C++ 代码互操作.

如果 C 给 Rust 一个已经签名的函数指针,
Rust 如果当普通指针直接调用,
就可能认证失败或产生错误行为.

反过来,
Rust 暴露给 C 的函数指针如果没有按 ABI 正确签名,
C 侧也可能无法使用.

第二,
Rust 自己也无法充分利用 AArch64 Linux 上的硬件控制流保护能力.

这个提案计划先加入 `aarch64-unknown-linux-pauthtest` 目标,
然后支持 PAC-aware 的 C 互操作、C++ 互操作,
最后再考虑 Rust 原生 ABI 下的 pointer authentication.

## Rust-for-Linux-compiler-features (延续提案)

Linux kernel 想要使用稳定 Rust,
不仅需要语言特性稳定, 还需要大量编译器选项稳定.

这些选项包括架构相关 flag、sanitizer、codegen选项等等.

提案里列了一长串内核目前依赖的 unstable 选项.

25H2 时, 这个提案已经在跟踪这些 feature,
目标是尽量把内核正在使用的 unstable 编译器能力向稳定推进.

2026 年的版本仍然延续这个目标,
但它把时间跨度扩展到 2026 到 2027,
并且更明确地承认: 这个目标某种意义上是长期存在的.

因为即使当前列表都稳定了,
未来新硬件、新架构等等设施仍然可能带来新的编译器开关需求.

## stabilization-of-sanitizer-support (延续提案)

Sanitizer 对 Rust 仍然重要.

虽然 safe Rust 能防住内存读写错误和并发读写错误,
但现实项目里有 unsafe Rust, 也有 C/C++ 混合链接.

这些边界上的问题,
仍然需要 AddressSanitizer、MemorySanitizer、ThreadSanitizer 这类工具发现.

25H2 时, 目标已经是稳定 MemorySanitizer 和 ThreadSanitizer,
并解决一个关键问题: 用户不能每次都靠 nightly 加自己重新构建标准库.

因为 MSan 和 TSan 这类工具需要 instrumented standard library.
如果标准库本身没有被插桩, 检测结果就不完整.

2026 年继续这个方向, 并提到一个新进展:
Rust 已经合入了一个新的 Tier 2 target,
用于让 AddressSanitizer 可以和 stable compiler 配合使用.
接下来计划用类似路线推进 MemorySanitizer 和 ThreadSanitizer.

## BorrowSanitizer (延续提案)

传统 AddressSanitizer 更擅长抓 use-after-free、越界访问这类问题.
但 Rust 还有一类更 Rust-specific 的错误: 违反 aliasing model.

今天能检查这类问题的主要工具是 Miri.
但它是解释MIR执行, 速度比原生执行慢很多, 而且对 FFI 场景支持有限.
这在大型 C++/Rust 混合项目里是个问题.

BorrowSanitizer 想做的是:
像 LLVM sanitizer 那样, 在编译时插桩,
运行时检测 Rust aliasing model.

25H2 有一个相关提案叫 `codegen_retags`, 它做的是更底层的铺垫:
让 MIR 里的 Retag 信息能够进入 codegen backend,
从而让 LLVM 层的工具知道引用什么时候被创建、更新、重新标记.

2026 年的 BorrowSanitizer 就是在这个基础上往前走.
它的目标包括:
完成 retag intrinsics 的 MCP 和实现,
让 BorrowSanitizer 在 aliasing 检测上尽量达到 Miri 的功能覆盖,
做自动化评估和 benchmark,
并讨论是否把 runtime、instrumentation pass 等组件集成进 rust-lang/rust 或独立仓库.

## wasm-components

现在 Wasm Component Model 和 WASI 0.3 正在推进,
其中一个核心变化是: Wasm 组件在 ABI 层面开始支持 async 操作.

Rust 如果想继续保持 Wasm 支持优势, 就需要跟上这套新平台能力.

提案列了几个目标:

把 `wasm32-wasip3` 提升到 Tier 2 支持.
新增 `wasm32-component` `wasm32-component-web` Tier 3 target.

此外还会尝试为 WASIp3 实现 `std::thread`,
以及探索 `#[repr(wasm)]`、`extern "wasm"` 这类 Wasm 原生语言接口.

## high-level-ml

这个提案的目标很野:
让 Rust 未来能更好地支持机器学习、高性能计算和科学计算.

过去几年,
Rust 编译器已经开始接入一些 LLVM 生态能力,
比如自动微分和 GPU offload.

提案里提到,
`std::autodiff` 已经启用到 nightly,
`std::offload` 会在 rustc 更新到 LLVM 22 后继续推进.

如果和 25H2 的 `finishing-gpu-offload` 放在一起看, 进展很明显:

25H2 还主要关注把 `std::offload` 模块补完,
让 Rust 能把代码发到 GPU 运行.

2026 年的 `high-level-ml` 开始把问题抬高一层:
光有 autodiff 和 GPU offload 还不够,
机器学习真正需要的是高层矩阵和张量优化.

比如识别 matmul、conv2d 这样的操作,
替换成更高效的实现;
或者把一串矩阵操作重排、融合、批处理.

很多加速器厂商都把 MLIR 当成输入格式.

所以这个提案想探索一个基于 MLIR 的 rustc 后端原型:
先瞄准一个加速器,
支持一个常见操作,
比如矩阵乘法,
再展示一个高层优化.

提案还特别强调:
最好不要强行把某一个 Matrix 类型塞进标准库.

Rust 生态已经有 faer、ndarray、nalgebra 等不同矩阵库.

如果编译器优化只能服务某个钦定类型,
就会破坏生态竞争.

更理想的未来是:
Rust 代码保持普通 Rust 的样子,
编译器能在合适位置识别和优化高层操作.

这当然还很远.

但它说明 Rust 团队已经不只是想让 Rust "能写系统软件",
也在认真探索 Rust 能不能进入 ML/HPC 这种长期被 Python、C++、Fortran、Julia 主导的领域.
