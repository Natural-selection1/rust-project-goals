# 语言特性: 易用性

## ergonomic-rc

只要你写过 async rust, 大概率都见过这种代码:

先 clone 一堆 `Arc`,
再通过 move 关键字, 让闭包以值捕获的方式捕获这些 clone 后的变量.
有些时候, 逻辑本身的行数可能都比不上这些的样板代码.

这个延续提案里的两个想法, 现在都可以在 nightly 上试了.

第一个是 `Share` trait. 想想 `Arc::clone` 和 `String::clone`.
前者让两个句柄指向同一份数据, 后者会复制字符串内容.
`Share` 专门表达前一种语义. 它的 `share()` 方法调用 `Clone::clone`,
标准库已经为 `Arc`、`Rc` 和 `std::sync::mpsc::Sender` 等类型实现了它.

第二个是 `move(expr)`. 它决定了括号里的表达式什么时候求值, 以及捕获什么.
比如下面这段示意代码, 在 nightly 上需要打开 `move_expr` 和 `share_trait`:

```rust
use std::clone::Share;

tokio::spawn(async {
    send_data(move(tx.share())).await;
});
```

创建这个 async 块时, `tx.share()` 就执行了, 返回的新句柄随即被移进 future.
等任务被轮询时, `send_data` 拿到的就是那个句柄. 外层还可以继续用原来的 `tx`.
9 月合入的编译器实现已经支持 async 块和 async 闭包, `move(expr)` 的 RFC 仍在讨论中.

## afidt-box

Rust 在 1.75 稳定了 trait 中的 async fn.

```rust
trait HttpClient {
    async fn fetch(&self, url: &str) -> Response;
}
```

但问题是, 这样的 trait 并非动态兼容.
每个实现的 `fetch` 都可以返回不同大小的 future.
泛型调用知道具体的实现, 通过 `&dyn HttpClient` 调用时, 调用方却不知道要给返回值留多少空间.

今天常见的解决方案是使用 `async-trait`. 它会改写 trait 的方法签名,
让实现者返回装箱的 future, 连泛型调用也要承担这次装箱.

现在的提案分两步走. 第一步是把 dyn 兼容性的判断细化到方法:
即使 `fetch` 还不能动态分发, 同一个 trait 里其他满足条件的方法也能通过 `dyn` 调用.
10 月, 负责人报告说这一步已经有了本地的初步实现.

第二步才是让 `fetch` 本身也能通过 `dyn` 调用, 由调用方决定为 future 装箱.
目标文档给了一个计划在 nightly 上试验的写法:

```rust
std::preview::dyn_box!(client.fetch(url)).await
```

这样, trait 作者可以照常写原生 `async fn`, 泛型调用也无需为动态分发付出装箱成本.
这个宏是第二阶段的设计示意, 最终语法仍然开放.

## field-projections (延续提案)

如果你有 `let foo_ref: &mut Foo = &mut foo`,
那你可以自然地写出 `let bar_ref: &mut Bar = &mut foo_ref.bar`,

这里把对整个结构体的可变借用缩小到了它的一个字段, 这一步就叫字段投影.

但如果你手里不是普通引用,
而是 `Pin<&mut T>`、`NonNull<T>`、`&mut MaybeUninit<T>`,
以及其他自定义智能指针, 事情就没这么简单了.

这些类型在语义上明明也能指向那个结构体的字段,
但 Rust 目前并没有一个通用机制来完成这样的事情,

这个提案的目标, 就是把这种能力推广到自定义指针类型.
25H2 时, 这个提案的重点还是找设计方向, 2026 提案则更进一步.

上一阶段提出了 `virtual places`, 试着让指针类型自己定义怎样读、写或借用一个位置.
今年 RustWeek 上, 团队展示了这个思路的新设计, 引入了 handle.
拿前面的可变借用来说, 投影到 `bar` 这一步可以先得到一个 `MutHandle<'a, Bar>`.
它表示在这段生命周期里可以可变借用这个字段, 再执行借用操作才得到 `&'a mut Bar`.

为什么值得多这一层? 想象一批二维坐标, 所有的 x 存在一个数组里, 所有的 y 存在另一个数组里.
内存里没有单独一个完整的 `Point`, 但在设计示例里, 仍然可以写 `points[i].x` 来操作第 i 个点的横坐标.

这套设计和手工展开的例子已经收进 Rust 项目的 beyond-refs 文档.
编译器侧也有了试验 `raw_handle!` 的 PR, 目前还在评审.

# 语言特性: 编译期能力

## const-generics (延续提案)

今天 Rust 已经稳定了 const generics 的 MVP,
你可以写类似 `[T; N]` 这种带常量参数的类型.

但它仍然有两个很明显的断崖:

第一, const generic 参数类型很有限.
主要是整数、`bool`、`char`.
在稳定版里, 即便是自己定义的简单枚举, 也不能拿来当 const 参数的类型.

第二, 就算参数类型只是 `usize`, 想用泛型关联常量写一个数组长度, 比如 `[u8; T::LEN]`, 在稳定版里也会遇到限制.

这两个限制, 今年分别有了进展.
参数类型这边, nightly 已经有 `min_adt_const_params` 实验.
难点之一是带私有字段的结构体: 如果编译器能推断出常量值, 怎样保证这个值满足类型作者维护的不变量?
负责人在 7 月提出先缩小稳定化范围, 从元组、数组和没有数据字段的枚举考虑起.

数组长度这边, 年初的 `min_generic_const_args` 原型已经发展成一组 nightly 特性, 统称 Generic Const Arguments, 简称 GCA.
比如现在可以用 `[u8; gca!(T::LEN)]` 表达刚才的数组长度, 让每个实现自己决定要留多少个字节.
这一组里, `gca_min_const_items` 和 `gca_const_items` 管哪些常量能用在类型里,
`gca_adts` 则允许用泛型参数构造结构体、元组或数组常量.
到 11 月, 用 `gca!` 定义的关联常量也已经可以在函数体里使用了.

## const-traits

今天很多代码其实都适合放到编译期跑,
比如构造查表数据、校验常量、做一些可提前计算的泛型逻辑.

但只要逻辑里涉及 trait, 就很容易撞墙.

比如你想在 const fn 里使用 iterator,
或者用 `?` 处理 `Result`, 它们背后都依赖 trait.

如果 trait 方法不能在 const 上下文调用,
那 `const fn` 的泛型能力就会被大幅削弱.

这个提案的状态比较有意思:
编译器里已经有相对成熟的 const traits 实验实现,
标准库里也已经有部分代码开始使用.

今年 9 月, 作者在原 RFC #3762 的基础上提交了新一版 RFC #4008, 并和语言团队开了设计会.
新版先圈出一个较小的范围: trait 可以标记为允许 const 实现, 具体的 impl 可以承诺自己的方法能够在常量求值时调用.
比如计算一个常量时要用 `T::default()`, 编译器就需要知道选中的实现能在编译期执行.

截至 11 月, RFC 仍在讨论. 作者接下来要做的是整理设计会和评审中的反馈, 再修改提案.

如果 const traits 能稳定,
它会让 `const fn` 从"只能写比较直接的过程逻辑",
变成"可以写真正泛型化的编译期逻辑".

## min-type-reflection (延续 reflection-and-comptime)

今天 Rust 生态里, 如果你想让一个库处理任意用户类型,
最常见的方式是让用户 derive 某个 trait.

比如序列化需要 `#[derive(Serialize)]`,
游戏引擎可能需要 `#[derive(Component)]`,

这带来一个问题: 库之间互操作很难.

每个库都希望用户为自己的类型加 derive,
但类型作者不可能为所有潜在库都提前写好实现.

这个提案想探索另一条路:
在编译期通过 `const fn` 获取类型信息,
让库可以对任意类型做结构化处理,
而不一定要求用户提前 derive.

25H2 时,
这个提案的目标还是:
设计并实验性落地一个基于 `const fn` 的反射方案,
同时加一个只能编译期调用的 const fn 机制.

现在这个目标改名叫 min type reflection, 时间跨度是 2026 到 2027 年.
最早的原型让你调用 `TypeId::info` 拿到一整份类型描述. 今年团队改成了按需查询的设计:
要打印一个结构体, 就查询它的字段. 要处理枚举, 再查询它的变体. 库只需要为自己实际用到的信息付出计算成本.

另一块基础也已经合入编译器了. 6 月合入的原型用内部属性 `#[rustc_comptime]` 标记只能在编译期调用的函数.
这样, 查询类型信息的那一步可以交给编译器完成, 程序运行时仍然可以用查到的信息来打印值.

已经有个演示能看出它的用途: 如果类型实现了 `Debug`, 就用类型自己的格式. 否则, 就通过反射把它打印出来.
团队接下来要厘清跨模块能看到哪些字段, 以及哪些信息变化会影响兼容性, 再争取在 2027 年稳定支持这类用途的最小 API.

## macro-improvements

Rust 的宏系统有两大类: 声明式宏 和 过程宏.

声明式宏编译快、无依赖、能使用 `$crate` 等机制, 但能力有限.

过程宏能力强, 但缺点也明显:
通常要单独建一个 proc-macro crate. 为了分析输入、生成代码, 宏作者还常常会引入 `syn`、`quote` 等依赖, 这些都会增加编译开销.

这里已经有两种可以在 nightly 上试的能力了. 一种是用 `macro_rules!` 写属性宏,
另一种是用它写 derive 宏. 对应的两个开关分别叫 `macro_attr` 和 `macro_derive`.
它们的初版实现都在 2025 年合入. 今年 9 月, 负责人说准备提出稳定化, 两个特性目前仍在跟踪中.

更远一步的想法叫 `macro fn`: 它还需要编译器能在宏展开时执行编译期求值.
前面讲的 comptime 函数原型解决了函数可以在哪里被调用的问题, 而让宏展开器在那个阶段运行这些计算, 还需要另外的工作.
此外, 团队也在探索 macro fragment fields 和 metavariable expressions.
