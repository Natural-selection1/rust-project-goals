# 语言特性: 易用性

## ergonomic-rc

只要你写过 async rust, 大概率都见过这种代码:

先 clone 一堆 `Arc`,
再通过 move 关键字, 让闭包以值捕获的方式捕获这些 clone 后的变量.
有些时候, 逻辑本身的行数可能都比不上这些的样板代码.

作为延续提案, 它经历过很多的设计, 现在提案提出两个更基础的能力:

第一个是 `Share` trait, 它用来表达一种语义:
这个类型 clone 之后, 得到的不是一份独立数据,
而是指向同一个对象的另一个别名.

比如 `Arc<T>`、`Rc<T>`、channel sender, 都可以实现 `Share`.

这样一来, 代码里写 `tx.share()` 时,
读者就知道这不是深拷贝, 而是在创建另一个共享句柄.

第二个是 `move()` 表达式.
它让你可以把捕获动作写在使用位置:

<!-- 这里需要更细致地解释一下 move() -->

这两个特性合起来, 让代表 资源handle的克隆 在闭包里的使用更紧凑

```rust
tokio::spawn(async {
    send_data(move(tx.share())).await;
});
```

## afidt-box

Rust 在 1.75 稳定了 async fn in trait.
你可以写:

```rust
trait HttpClient {
    async fn fetch(&self, url: &str) -> Response;
}
```

但问题是, 这样的 trait 并非动态兼容.
原因在于 async fn 返回的是一个隐藏的 future.
动态分发时, 调用方不知道被调用者会返回多大的 future.

所以今天常见的解决方案是使用 `async-trait`
但它的问题是会改变 trait 定义本身:
trait 的实现者也被迫每次都返回 boxed future.

这个提案通过引入 `.box` 后缀表达式,
让 trait 定义保持原生 async fn, 保持泛型调用的零分配,
只有在你真的通过 `dyn` 调用时, 由调用点显式 box.

```rust
client.fetch(url).box.await
```

`.box` 的意思是:
我知道这里需要一次堆分配, 我也接受这个成本.

这与 Rust 的理念一致:
堆分配应该可见, 但也不要让用户为了表达常见模式写一大坨类型.

这个提案还会推动一个更细的概念: method-scope dyn compatibility.
也就是说, 一个 trait 不再只是简单地分成"整个 trait 是否动态兼容".
某些方法也许只有在指定分配策略时才能通过 dyn 调用.
这对 async trait 很重要, 未来对 RPIT 这类返回不定大小值的方法也可能重要.

## field-projections (延续提案)

如果你有 `let foo_ref = &mut foo`,
那你可以自然地写 `let bar_ref: &mut Bar = &mut foo_ref.bar`,
得到某个字段的可变引用.

但如果你手里不是普通引用,
而是 `Pin<&mut T>`、`NonNull<T>`、`&mut MaybeUninit<T>`,
或者某个自定义智能指针, 事情就没这么简单了.

这些类型在语义上明明也能指向那个结构体的字段,
但 Rust 目前并没有一个通用机制来完成这样的事情,

所以生态里会出现很多专门的宏和 crate,
比如 pin projection 相关工具.

这个提案的目标, 就是把这种能力推广到自定义指针类型.
25H2 时, 这个提案的重点还是找设计方向, 2026 提案则更进一步.

上一阶段形成了一个新方向, 叫 `virtual places`.
它的想法是:
不要只把字段投影理解成"拿到某个真实内存地址",
而是把它抽象成对 place 的操作.

因为有些类型的字段, 可能并不对应一个简单的真实内存位置.

提案里提到的设计会引入类似
`PlaceRead`、`PlaceWrite`、`PlaceMove`、`PlaceBorrow` 的 trait,
允许类型定制该如何读取、写入、移动和借用一个虚拟位置.

这听起来很底层, 但它的最终目标其实很朴素:
让 `NonNull<T>`、`MaybeUninit<T>`、`Pin<&mut T>`、Rust for Linux 里的各种指针类型,
都能自然地访问它们的字段.

## pin-ergonomics (延续提案)

`Pin` 是需要 Rust 功能的重要基础, 但问题在于它写起来非常不舒服.
很多时候你只是想表达: 我现在要以 pinned 的方式借用这个位置.
但实际代码往往要绕过一堆 API、宏和 unsafe 边界.

25H2 时, 这个提案已经开始探索 `&pin mut place` 这样的语法,
还列出了 pattern matching、coercion、auto borrowing 等工作.
2026 年的版本仍然是继续实验, 但它把一个关键语义问题说得更清楚了.

普通 `&mut` 借用是临时的, 借用结束, 原来的 place 又恢复正常.
但 `&pin mut` 不一样, 一旦一个 place 被 pin 过,
这个 pinned 效果可能在借用生命周期结束后仍然存在.

也就是说, 你不是"临时借一下",
而是在程序语义里永久改变了这个位置的可移动别.

相较于 25H2, 它不是简单地"继续把语法写完",
而是把重心推进到了 borrow checker 支持、coercion、auto borrowing,
以及这种新借用行为是否可理解的问题上.

# 语言特性: 编译期能力

## const-generics (延续提案)

今天 Rust 已经稳定了 const generics 的 MVP,
你可以写类似 `[T; N]` 这种带常量参数的类型.

但它仍然有两个很明显的断崖:

第一, const generic 参数类型很有限.
主要是整数、`bool`、`char`.
目前不能把 ADT 当成 const 参数.

第二, const 参数位置能写的表达式也很有限.

比如你想写 `Foo<T::ASSOC_CONST>`,
使用某个关联常量作为 const 参数,
现在仍然会遇到限制.

25H2 时, 这个提案主要目标是:
为 `adt_const_params` 整理设计文档和 RFC,
并继续完成 `min_generic_const_args` 原型.

2026 年的目标更清楚:

一条线是 `ADT const params`.
也就是让 struct、enum、tuple、array 等 ADT 可以作为 const 参数.

另一条线是 `min_generic_const_args`.
也就是让关联常量和泛型参数能更自然地出现在 const 参数表达式里.

## const-traits

今天很多代码其实都适合放到编译期跑,
比如构造查表数据、校验常量、做一些可提前计算的泛型逻辑.

但只要逻辑里涉及 trait, 就很容易撞墙.

比如你想在 const fn 里使用 iterator,
或者用 `?` 处理 `Result`, 它们背后都依赖 trait.

如果 trait 方法不能在 const 上下文调用,
那 `const fn` 的泛型能力就会被大幅削弱.

这个提案的状态比较有意思:
编译器里已经有相对成熟的 const traits 实验实现,
标准库里也已经有部分代码开始使用.

但它还缺一个被正式接受的 RFC, 来确定语法和语义.

所以 2026 年的目标就是:
继续完善 const traits RFC,
处理现有反馈, 补齐必要的编译器工作,
发起测试, 然后推进稳定化.

如果 const traits 能稳定,
它会让 `const fn` 从"只能写比较直接的过程逻辑",
变成"可以写真正泛型化的编译期逻辑".

## reflection-and-comptime (延续提案)

今天 Rust 生态里, 如果你想让一个库处理任意用户类型,
最常见的方式是让用户 derive 某个 trait.

比如序列化需要 `#[derive(Serialize)]`,
游戏引擎可能需要 `#[derive(Component)]`,

这带来一个问题: 库之间互操作很难.

每个库都希望用户为自己的类型加 derive,
但类型作者不可能为所有潜在库都提前写好实现.

这个提案想探索另一条路:
在编译期通过 `const fn` 获取类型信息,
让库可以对任意类型做结构化处理,
而不一定要求用户提前 derive.

25H2 时,
这个提案的目标还是:
设计并实验性落地一个基于 `const fn` 的反射方案,
同时加一个只能编译期调用的 const fn 机制.

2026 年的文档里出现了一个很关键的进展:
MVP 已经落地.

它实现了 `TypeId::info`, 可以返回一个 `Type` 结构,
里面包含类型种类等信息.
现在还在逐步增加更多 `TypeKind`,
并且已经有基础的 comptime fn PR 在推进.

2026 年的目标, 是继续完善这个实验:
增加 `Type` 和 `TypeKind` 信息,
处理跨模块访问 private 字段时的隐私问题,
给 const fn 加只能编译期调用的属性,
并最终争取 lang 和 libs-api 的认可.

作为 MVP 的推进, 它明确把范围限制在:
产生 const eval 值, 让程序可以在编译期读取类型结构信息.
至于把类型信息重新塞回类型系统, 那是后续阶段的事情.

## macro-improvements

Rust 的宏系统有两大类: 声明式宏 和 过程宏.

声明式宏编译快、无依赖、能使用 `$crate` 等机制, 但能力有限.

过程宏能力强, 但缺点也明显:
必须单独建一个 crate,
引入 `syn`、`quote`、`proc-macro2` 等重依赖,
也会拖慢 `cargo check`.

这个提案的初始目标,
是稳定声明式 attribute macro 和 declarative derive macro.

也就是说, 让一部分今天必须用过程宏写的东西,
未来可以用更轻量的风格表达.

更长期看,
这个提案还会探索 macro fragment fields、metavariable expression,
以及和 reflection/comptime 配合的 `macro fn`.
