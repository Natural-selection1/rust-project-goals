# Rust 2026 提案导读

大家好, 欢迎来到下划线下划线自然选择下划线下划线的频道.

2026 年 5 月 14 号 Rust 更新了 2026 年的提案状态.
同时也修改了提案发布的节奏, 由之前的半年发布一次, 修改为一年发布一次.
因此这次的提案数量相较于 25H2 也有明显的增加.

在 2026 提案中, 25 个是 25H2 的延续提案, 同时有 41 个新提案,
之前使用的五种提案分类也不再适用.

我将它们分成了以下十类, 计划以四五期视频分步解读.

# Cargo与Crate

首先来看 `Cargo与Crate` 主题

## cargo-lints

作为一名rust开发者,
你肯定熟悉那些由rustc, clippy 甚至于 rust-analyzer 提供的lint.
那紧致的包裹感让人安心, 也让我们参与其他项目时更加轻松,
不会把时间浪费在不必要的细节上.

然而 Cargo 本身却没有提供足够的检查能力,
这导致许多只会出现在 Cargo.toml 里的问题无法被发现.
最常见的便是导入的库因为代码变更而未被使用.
我们不得不借助 cargo shear 等 Cargo 插件来处理这类问题.

这个提案的目标就是将已经在 nightly 中实现的 Cargo 检查系统
优化至与 rustc 和 clippy 同等质量并稳定化.
让原生工具链能够覆盖rust项目中的方方面面, 而不仅仅是 .rs 中的代码.

## interactive-cargo-tree

理解项目依赖关系图、调试版本冲突,
以及分析依赖项中使用的features, 是 rust 项目 依赖管理的常见需求.

Cargo 目前提供的 tree 指令用于输出项目的依赖树, 但其目前仅为静态工具, 缺乏交互性.
探索大型或复杂的依赖关系图十分困难, 不得不管道传递给 ripgrep 等工具做额外处理.

这个提案想为 cargo tree 添加交互模式，提升探索依赖图的体验.
这将允许用户通过按键对依赖图执行操作, 并提供额外的功能和视觉改进.
用户将能够更高效地导航和分析其依赖图.

### open-namespaces (延续提案)

对于一个大型 rust 项目而言, 其必然由多个 package 组成.
这些 package 之间往往联系紧密, 更像是一个整体而不是几个独立的包.

但如果想将它们各自发布, 就会面临一个问题:
怎么表示这个 package 是我发布的, 且与其他的包有关系?
目前的解决方案是手动添加"命名空间", 比如 tokio-util.
但这样的方式并非优雅, 如果其他人发布了 tokio-utils.
很多人可能并不知道自己导入了错误的包

这导致了信任危机, 开发者在使用类似命名方式的包时, 需要去确认它们是否是"官方出品"

这个提案希望引入命名空间, 允许 package 的作者在命名空间下发布其他的package.

对发布者而言:
可以将项目内部适合拆分的子模块，拆成命名空间下的独立 package 发布和维护.
它可以独立版本、独立依赖、独立发布.

对使用者而言:
可以从命名上直接判断哪些 package 出自官方, 避免信任危机
并且在代码中像使用 crate 的子模块一样使用这些子 package.

作为 25h2 的延续提案, 目前 Cargo 支持已部分实现, 编译器设计也已达成一致并部分实现

## 其他提案

这个主题下其他的提案用户感知并不明显, 我们简单过一下

### pub-priv (延续提案)

允许声明依赖库是否对外部可见.
能够防止意外暴露, 强化语义化版本检查, 同时减少文档噪音.
提案计划在这个提案年实现并稳定RFC中描述的公共依赖项的 MVP.

### cargo-plumbing (延续提案)

把 Cargo 从黑盒拆分成一系列模块化的底层命令,
让其他工具能更灵活地与 Cargo 集成.

去年本提案入选 GSoC, 因此取得了一些进展, 但目前对具体的实施方案仍处于重构当中

### stabilize-cargo-sbom

Software Bill of Materials是一份项目依赖项及其版本的列表，类似于 Cargo.lock
采用跨编程语言标准化的格式。它能够实现供应链透明度，并便于识别存在已知漏洞的依赖项.
在美国，第 14028 号行政命令要求联邦政府仅采购能提供每款产品软件物料清单的供应商产品。
在欧盟，《网络弹性法案》规定任何在欧盟销售的包含“数字元素”的产品必须在其技术文档中包含 SBOM

该提案解决 Cargo 的 SBOM 前驱功能中的已知问题并最终确定 RFC，
推进 Cargo SBOM 支持的 MVP 版本开发进度

### cargo-script (延续提案)

现在写个最简单的 Rust 程序, 最少也得创建 `Cargo.toml` 和 `main.rs` 两个文件.
这个提案就是要让 Rust 支持 "单文件脚本", 像 Python 那样, 一个文件就能跑起来.
目前其并没有遇到过多的阻塞问题, 主播预计这个提案年就能够完成

### cargo-semver-checks (延续提案)

在 `cargo publish` 时自动检查语义化版本约束,
阻止发布者做出违背语义化版本的 API 变更.
其在2025年 Lint 数量由120个增长到242个, 而lint执行时间却减为原来的四分之一.
但其任有许多工作需要完成, 作者预计可能在2028年才能正式稳定.

# 编译器核心

`编译器核心` 主题主要聚焦于 rustc 的改进, 这也是 rust 拓展自己生态的重要手段

## library-api-evolution

Rust 标准库对 API 稳定性有着极其严格的承诺.
一旦某个 API 稳定下来, 必须永久保持不变.
这当然保证了向后兼容,
但也意味着我们很难去修复那些不够完美的设计.
例如 `Command` 的 API, 或者让 `Mutex` 默认不中毒等等.

目前，想修改标准库中的稳定 API 的唯一办法是
废弃旧 API 并引入一个新名字.
但这不仅让人在起名字时抓耳挠腮，而且还会给整个生态带来跟进压力.

这个提案引入了 基于 Edition 的重导出 方案.
它允许同一个标准库路径在不同的 Edition 中指向不同的底层实现。
这样一来，标准库可以通过 Edition 进行 API 演进,
而旧代码依然可以通过使用旧 Edition 保持兼容性。

## async-future-memory-optimisation && async-statemachine-optimisation

除了语法上的易用性外, 另一个阻碍 async 在rust生态中被广泛使用的原因,
便是 async 编译后的的状态机过于臃肿.

尤其当多个 async 函数嵌套起来, 最终状态机的体积会相当离谱.
这就会导致 future 明明逻辑不复杂, 但类型大小 一测大得吓人,
有可能带来难以解释的栈溢出, 嵌入式和内核场景里更是会直接劝退使用者.

这两个提案的核心目标, 就是优化状态机的生成.

`async-statemachine-optimisation` 负责在生成状态机时, 直接优化掉不必要的状态和分支.
`async-future-memory-optimisation` 负责让状态机内存更加紧凑.
未来还会探索两条更底层的路线:
一种是把被组合起来的 future 做更深的内联,
另一种是研究能不能更直接地利用 LLVM 自带的 coroutine 机制来做布局和优化.

## expansion-time-evaluation

Rust 离真正的编译期执行, 差的不是语法, 而是编译器架构.

今天, 宏展开、名称解析、trait 求解等等 耦合得太紧.
宏展开想知道某个类型或函数的信息,
但解析器又要整个 crate 展开完成后才能稳定工作;
trait 求解 默认还要看到当前 crate 里的所有 impl.

这导致编译器不能在“展开到一半”的时候暂停一下,
去编译并执行某个当前 crate 里的函数.

这个提案要做两件事:

第一, 给 trait 求解器加一个“受限模式”.
某些展开期运行的函数可以通过特殊标记,
使它们只看到上游 crate 的 trait impl.
看不到本 crate 还没完全展开的内容,
以避免“编译期函数的执行结果反过来影响它自己的可见 impl 集合”这种循环依赖问题.

第二, 是把现在一体化的求解器做 query 化改造.
让编译器更像一个真正可中断、可局部求值的系统,
为 `macro fn` 或其他 `crate 内操作逻辑` 提供实现路径,
甚至为编译器内建的互操作生成器铺路.

## 其他提案

剩下的提案中, 也有 next-solver 和 polonius 这样的重量级,
让我们一起看看吧

## dictionary-passing-style-experiment

今天 Rust 编译器在很多阶段会“事后再推一遍 trait 结论”
类型检查时算过一次, 到了借用检查、代码生成等后续阶段,
又会按需把对应 impl 重新找一遍.

这个提案就是想在 rustc 里试验这种 字典传递风格.
在前面把“这个约束到底由哪个 impl 满足”一次性决定好.

## assumptions_on_binders

今天 Rust 在处理 `for<'a>` 这类 binder 时,
并不会完整记录那些和被绑定生命周期相关的 where 约束.
这导致编译器在遇到高阶生命周期约束时会遗忘信息.
轻则报出让人摸不着头脑的错误, 重则出现健全性问题.

这个提案的目标,
是把今天只在有限场景内工作的 `-Zhigher-ranked-assumptions` 特性,
重新设计成对所有 binder 都适用的通用机制.

## mir-move-elimination (延续提案)

在rust中, 值经常先在某个地方构造出来, 再被 move 到最终位置.
理论上, 编译器应该尽量把这些 move 消除.
但在实践里, 一旦对象的地址被观察过, rustc 往往不敢做这件事,
最后落成不少 `memcpy` 或栈到栈的复制.

提案的核心想法, 是修改 MIR 中 `move` 操作的语义.
如果一个值被 move, 其分配区域就能被视为“释放出来了”,
从而让后续局部变量有机会直接复用那段存储.

作为延续提案, 其在今年4月1号正式公开了最新的 RFC.
并且在实验性分支上已经能够为rustc带来2-5%的性能提升

## next-solver (延续提案)

Rust 的 trait 系统很强,
但支撑它的 trait 求解器却已经背负了太多历史包袱,
以及有许多长期存在的健全性问题.

`next-solver` 的目标,
就是把 trait 求解从“到处散落的选择逻辑”
改造成一个更统一的 goal solving 系统.

编译器不再只是问“这个约束该选哪个 impl”,
而是把问题表达成“在当前参数环境下, 这个 goal 能不能被证明”.

它希望最终完全替换旧 trait solver,
负责 trait bound 证明、关联类型归一化等核心工作,
同时修复长期存在的健全性问题, 解锁未来类型系统能力,
并尽可能改善编译时间。

## polonius (延续提案)

如果说 `next-solver` 是 Rust 类型系统的地基翻新,
那 `Polonius` 就是 Rust 借用检查器的核心升级.

今天的 NLL 已经不再简单认为一个引用活到整个 `{}` 作用域结束,
而是基于 MIR 和控制流判断引用实际活跃到哪里,
但 NLL 仍然有自己的表达极限.

比如“查到了就返回引用, 查不到就插入再返回”这一类代码.
人能看出两个分支互不冲突, 但当前借用检查器有时会认为:
既然某个分支把引用返回出去了,
那这个容器在整个函数后续路径里都可能还处于被借用状态.

`Polonius` 的思路是换一种方式理解借用.

它不再把生命周期看成“哪些程序点还活着”,
而是把它看成一个“来源域”.

这个来源域里记录的, 不是一段抽象的存活范围, 而是若干次具体的借用项。

于是借用检查器要回答的问题,
就从过去的: “这个生命周期覆盖了哪些程序点?”

变成了: “在当前这个程序位置, 这个来源域里可能包含哪些具体借用?”

Polonius 可以沿着控制流,
在每个程序位置分别计算这些借用项之间的包含关系。

某个借用只在 `Some` 的分支里存在,
就不应该污染 `None` 分支;

某个引用已经被覆盖掉,
它携带的旧借用也不应该继续影响后续判断。

这也是 Polonius 和 NLL 最核心的区别:
NLL 更像是在追踪“生命周期覆盖到哪里”,
而 Polonius 更像是在追踪“具体借用从哪里流到了哪里”.

最新的 CI 提案也说明,
Rust 团队准备 让 Polonius alpha 和 next-solver 进入rust的CI流程
比较它们在真实编译器测试中的行为差异,
以便在稳定化前持续发现回归。
