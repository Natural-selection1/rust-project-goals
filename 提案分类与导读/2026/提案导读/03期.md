# Cargo与Crate

## crates-io-supply-chain-hardening

供应链攻击, 想必各位都不陌生.
除了预防之外, 还有一件非常重要的事情是, 管理员发现问题之后, 应该怎么处理?

最熟悉的办法是 yank, 但 yank 主要影响的是新一轮的依赖解析.
如果这个版本已经写进你的 lock 文件, Cargo 仍然可以下载它.

这对于普通的坏版本很合理, 但对于已经确认有问题的恶意版本, 就不够了.

直接删除当然更彻底, 但删除会影响历史数据, 恢复也不完整.
管理员需要在很短的时间里, 决定是否采取这种破坏性操作.

这个提案希望补上中间的一步: 隔离.

先暂停可疑版本的分发,
即使它出现在已有的 lock 文件中, 也不能继续被获取.
同时保留包的归属和历史数据, 让后续调查和恢复更容易进行.
提案还设计了可逆、可审计的撤回状态, 改善直接删除带来的问题.

有了这套机制, 自动检测系统就可以参与其中.
对于高度可疑的版本, 先自动隔离, 再交给人工复核.
它要缩短的, 是攻击发生后, 仓库仍然在继续分发恶意版本的那段时间.

- 2026 目标页: https://goals.rust-lang.org/2026/crates-io-supply-chain-hardening.html
- tracking issue: https://github.com/rust-lang/goals/issues/816
- 提案引用的 PyPI 隔离机制: https://blog.pypi.org/posts/2024-12-30-quarantine/

# 编译器核心

## borrowck-fcw

Future Compatibility Warning.

修复编译器的 bug, 有时会让用户的代码编译失败.
但如果更新工具链之后直接报错, 用户往往没有准备.
所以需要一种办法, 提前告诉大家哪些代码将来会不兼容.

提案描述的就是这种能力.

编译器可以比较新旧两套借用检查的结果,
识别哪些错误是新规则带来的,
再为适合分阶段迁移的变化提供警告和过渡.

NLL 迁移时用过类似机制,
但借用检查器后来发生了不少内部变化, 旧设施已经不容易继续复用.
这次要重构诊断和比较机制, 让后面的规则调整更容易平稳落地.

### polymorphization

Rust 通常会对泛型做单态化代码生成,
这给优化器提供了很充分的信息.
但实例多了, 编译器就得重复处理更多函数,
最后生成的中间产物和二进制也会更大.

提案想尝试让一部分泛型实例共享代码.

比如函数分别使用 `&u32` 和 `&String` 作为类型参数.
因为引用本身的布局相同, 就有机会共用一份函数实现.

如果函数需要调用 trait 方法, 或者需要知道怎么析构这个类型,
编译器就通过隐藏参数, 把对应的方法指针和类型信息传进去.

这里仍然保留具体数据的布局, 共享的是适合共享的函数代码.
而且同一个函数里, 一些类型参数可以这样处理, 其他参数仍然单态化.

把部分信息传到运行时, 让不同实例共享代码, 代价也很直观.
多了间接调用, 也可能减少内联机会, 运行时性能需要重新权衡.

查验链接（后期用, 不用念）:

- 2026 目标页: https://goals.rust-lang.org/2026/polymorphization.html
- tracking issue: https://github.com/rust-lang/goals/issues/758

### turbofishing-late-bound

Rust 泛型与其他语言泛型的一大重要区别是, 生命周期是泛型参数的一等公民.
这就导致了 Rust 实例化泛型存在两种时机, `命名函数时` 与 `调用函数时`
这两个时机分别被叫做 early bound 和 late bound.

直接从函数名调用时, 这两个步骤连在一起.
但是先获取函数项再使用它时, 差异就会显现出来.

其中类型泛型参数和常量泛型参数都是 early bound.
而生命周期泛型参数则根据其使用情况决定其 bound 时机.

当且仅当满足下面这两个条件时, 该生命周期泛型参数是 late bound:
首先其不可以在 where 子句中被使用, 其次也必须受参数类型约束.

背景知识介绍完了, 接下来这个提案大伙就可以看懂了.

```rust
fn foo<'a, T>(value: &'a T) -> &'a T {
    value
}

fn main() {
    let foo_fn = foo::<u32>;
    let n = 42;
    assert_eq!(*foo_fn(&n), 42);
}
```

这里的 `let foo_fn = foo::<u32>` 就是在取得一个函数项.
这里已经将类型泛型参数 `T` 实例化为了 `u32`,
之后通过同一个 `foo_fn` 调用, 就不能再换成其他类型的引用.

接下来, 因为这里的生命周期泛型参数 `'a` 符合条件, 所以是 late-bound.
这意味着取得 `foo_fn` 函数项时, 生命周期泛型仍然保留在调用签名中,
不同调用位置可以分别实例化这个生命周期参数.

所以在这里, 如果我们想明确写出 `foo_fn` 这个变量的类型, 就是下面这样:
`for<'a> fn(&'a u32) -> &'a u32`
这里的 `for<'a>` 读作 "对任意生命周期 `'a` 都有".

有些时候, 我们已经知道了明确的生命周期参数, 可以直接实例化.
但因为 late bound, 现在不支持使用 turbofish 直接指定它.
也就是说, 当前可以写 `foo::<u32>`, 却不能写 `foo::<'static, u32>`.

但我们可以换一种方式:

```rust
let foo_fn: fn(&'static u32) -> &'static u32 = foo::<u32>;
```

这里把函数项转换成了函数指针.
原函数对任意生命周期都适用, 自然也能满足 `'static` 这种具体要求.
但转换成特定签名的函数指针, 不等于直接给原函数项指定 late bound 参数.

提案想补上的, 就是后者的表达能力.

它探索给 函数项的内部表示 引入 binder,
让编译器能记录哪些参数已经指定, 哪些还保持通用,
再配套修改泛型参数处理和借用检查.

目前具体方案仍在探索.
特别是有多个 late bound 参数时, 能不能只指定一部分,
其余参数如何继续保留通用性, 语法和细节都还没有定论.

### compiler-performance-optimization

提案见名知意, 其旨在关注持续的性能剖析, 找到热点之后, 一项一项地改.

### tpde

TPDE 是一个以快速生成机器码为目标的编译器后端框架,
它读取 LLVM IR，输出机器码.
目前, 它相比 LLVM O0, 后端编译速度快十到二十倍.

提案计划把它作为现有 LLVM 后端中的实验选项, 并通过 rustup 分发所需的库.
先让足够多有代表性的 crate 跑通, 再看实际加速效果.

我们第二期讲过 Cranelift, 现在又多了一条值得验证的 debug 构建加速路线.

# 工具链

## 新提案

### process-safe-rustup

打开一个新项目, 它要求的工具链还没安装.
你在终端执行 `cargo build`,
编辑器里的 rust-analyzer 插件也在后台调用 Cargo.
两个调用都先经过 rustup 的代理程序, 安装过程就先撞上了.

原来的工具链操作虽然有事务和回滚,
但这套机制没有考虑另一个进程也在修改相同目录.

这个提案要设计新的事务机制,
让针对同一工具链的修改可以安全协调,
并考虑操作中途被打断的情况.

先保证多个进程不会互相破坏,
未来也可以在这个基础上继续探索工具链去重.

### rustc-public

如果你想读取程序中的一些编译相关信息,
直接使用 rustc 内部 API, 往往意味着需要频繁跟进编译器改动.
编译器内部一次正常重构, 外部工具可能就需要重新适配.

提案希望提供更适合外部工具使用的接口.

这次的目标是把首版发布到 crates.io,
同时补齐兼容性检测、测试、文档和 driver.
让接口有明确的版本, 发生破坏性变化时有说明和迁移指引.
这样外部工具就不必每次都从复杂的编译器内部结构里重新摸索.

# 文档

## 新提案

### executable-specification

第二期我们讲过,
Rust 需要明确的语言规则, 不能每次都靠翻编译器源码来找答案.

但即使写成了文档, 自然语言仍然可能有歧义.
两个人读同一段描述, 对边界情况的理解可能会有不同

这个提案想把规范写成带有解释文字的程序.
你既可以阅读它, 也可以把它运行起来,
用具体的 Rust 程序验证其中的规则.

它会从我们平时写的 Rust 语法出发,
通过一步步脱糖, 把复杂语法转换成更基础的结构.
每一步都有文字说明和转换前后的例子.
然后接到 a-mir-formality, 由它描述类型系统等静态规则,
再连接 MiniRust, 描述程序如何执行以及运行语义.

这两个项目已经有各自的模型,
但从实际 Rust 源码到这些模型之间, 仍然需要一座桥.

新提案主要就是把这条路径接起来,
除了读文字, 还可以运行例子, 检查模型行为, 发现遗漏和分歧.

- tracking issue: https://github.com/rust-lang/goals/issues/749
